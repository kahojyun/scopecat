## Summary

Fricon is valuable because it captured a serious first attempt at replacing a
fragile LabRAD/Data Vault-style measurement loop. It also shows why Scopecat
should not simply continue that direction: Fricon centered measurement history
and stable reopen before fully considering how to cover the real experimental
workflow progressively across intent, setup, code, calibration, analysis
handoff, lineage, and bounded automation.

The useful lesson is not "build Fricon again." The useful lesson is that
ordinary Python recording, durable measurement identity, explicit data shape,
checkpoint-safe reads, source identity, and low-ceremony reopen are important
substrates, but they are not enough to define Scopecat's product direction.

## High-Value Evidence To Preserve

- Ordinary Python and notebook-heavy acquisition are important adoption paths.
  Early recording should feel like a small explicit writer change, not a new
  managed framework.
- Stable run or measurement identity is valuable, but stable reopen by ID is
  only the start. Users also need selected context, companion artifacts,
  source paths as aliases, lifecycle state, and ambiguity warnings.
- Dataset shape pressure is broad: regular grids, partial grids, irregular or
  adaptive points, repeated points, trace-valued records, variable-length
  traces, multiple traces per outer record, complex values, IQ arrays, shot
  tensors, classified labels, and ragged optimizer or minimizer steps.
- Durable partial reads matter before resumable execution. Resuming a run
  requires runner cooperation and scan-point checkpoint semantics; readable
  partial data can be useful earlier.
- Live plots and dashboards should be disposable consumers. Durable writes and
  lifecycle records should not depend on a live view staying connected.
- Passive setup, procedure, parameter, registry, wiring, demod/readout, and
  runner summaries are useful context, but should not claim physical truth or
  authoritative setup ownership by default.
- Code provenance is a separate problem from execution. Copied folders,
  notebooks, helper packages, generated bytecode, lockfiles, and local
  environments need diagnostic identity before Scopecat accepts managed
  execution or deployment scope.
- Analysis handoff is distinct from acquisition. Derived arrays, plots,
  spreadsheets, decks, PDFs, reports, fit results, and JSON outputs need links
  back to source runs, selected context, correction choices, and manual
  judgment.
- Calibration and parameter work should first produce evidence, proposals,
  diffs, health gates, working refs, and audit trails before any mutation,
  rollback, or autonomous calibration is accepted.
- Export and handoff should preserve source identity, semantic context,
  checksums or integrity facts, and missing-context warnings, not only bytes.

## Design Mistakes To Avoid

- Do not let a dataset-first storage or browser model carry whole-run meaning.
  Dataset artifacts can own data-shape facts; scenario or run records should own
  lifecycle, context, provenance, and user intent.
- Do not let compatibility with prototype workspaces preserve the wrong domain
  model. Real post-reset records need durability; pre-reset test workspaces do
  not need to shape current design.
- Do not mix archived proposals, implementation facts, AI process notes,
  product plans, and domain decisions in one planning surface.
- Do not use Fricon personas or capability maps as current role or subsystem
  truth. Roles should stay scenario-local lenses until validated.
- Do not promote future runner, device, calibration, export, or AI automation
  surfaces before a validation slice validates the boundary and an ADR accepts the
  risky ownership.
- Do not infer public API, storage, reader, or UI shape from Fricon SDK
  sketches. Keep the product intent, not the names or object model.
